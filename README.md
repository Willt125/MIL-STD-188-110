# MIL-STD-188-110
A short, educational attempt at implementing a minimal MIL-STD-188-110C encoder/decoder.

The goal is a readable, heavily tested Python implementation of the fixed-frequency
serial-tone waveform (§5.3.2: 75–4800 bps, zero/short/long interleave). It produces
baseband I/Q from arbitrary data and recovers the data from baseband I/Q, via files or pipes.

- [`docs/walkthrough.ipynb`](docs/walkthrough.ipynb): one message through the modem, block by
  block, with plots. Start here.
- [`docs/CONFORMANCE.md`](docs/CONFORMANCE.md): every row of Table XVI (the standard's required
  bit error rates on HF channels), run for up to a million bits on the Appendix E channel
  simulator, generated by `tools/conformance.py`. Every row meets its requirement (600 bps:
  consistent with it).
- [`docs/PLAN.md`](docs/PLAN.md): scope, architecture, testing strategy and milestones.
- [`docs/VALIDATION.md`](docs/VALIDATION.md): checks against real 188-110A recordings (our
  transmitter reproduces a fielded modem's output symbol for symbol; the receiver decodes the
  recordings) and against an independent HF channel simulator.
- [`docs/PERFORMANCE.md`](docs/PERFORMANCE.md): how the receiver was designed and measured,
  milestone by milestone, including what was tried and did not work.
- [`docs/SPEC_NOTES.md`](docs/SPEC_NOTES.md): every ambiguity or error in the spec, and how
  this implementation reads it. Code and tests refer to these entries as `INT-nnn`.

## Transmitting

```sh
pip install -e .
m110c-tx --rate 2400 --interleave long message.txt -o signal.cf32   # complex float32 I/Q
cat message.txt | m110c-tx --format wav > signal.wav                 # 16-bit audio WAV
m110c-tx --async 8N1 --format s16 < message.txt | aplay -f S16_LE -r 9600
```

The output is complex baseband at 9600 samples/s with the carrier at +1800 Hz, so the real part
is the audio for an upper-sideband transmitter. Options: `--rate` 75–4800, `--interleave`
zero/short/long, `--format` cf32/cs16/s16/wav, `--sample-rate` (a multiple of 2400),
`--carrier`, `--async 8N1` (start/stop framing, Appendix A send-all mode), `--msb-first`,
`--voice` (2400 bps digital voice: the input is a vocoder's bit stream, see below).
`m110c-tx --help` lists them all.

## Receiving

```sh
m110c-rx signal.cf32 -o message.txt
m110c-tx < message.txt | m110c-rx > copy.txt                       # a loopback through pipes
m110c-rx --format wav --async 8N1 recording.wav                    # e.g. a real 188-110 capture
```

The receiver finds each transmission by itself: it searches ±400 Hz around the 1800-Hz
carrier, reads the mode from the preamble, follows timing (±0.2% clock error) and carrier,
estimates the multipath channel at every probe and equalises it, and stops at each
end-of-message marker before searching for the next. Two lines per message go to stderr:

```text
m110c-rx: 2400L preamble at 0.00 s, carrier 1800.3 Hz (+0.3), receiving
m110c-rx: 2400L at 0.00 s, carrier 1800.3 Hz (+0.3), clock +1 ppm, SNR 13.3 dB, 18000 bytes, EOM found
```

It works as a live stream: bytes come out 1–2 s after they were on the air (up to 6 s with
the long interleaver, 6–11 s at 75 bps, where the deinterleaver and the end-of-message check
dominate), using 0.1–0.4 s of one CPU core per second of signal (docs/PERFORMANCE.md, M12).
Options: `--async`/`--msb-first` (must match the sender), `--zero-interleave`,
`--invert-spectrum` (lower-sideband input), `--max-offset`, `--sample-rate` (a multiple of 2400;
resample other rates first, e.g. `sox in.wav -r 9600 out.wav`), `--no-equalizer` (the simpler
single-gain tracker of M8, for comparison), `--voice` (below).

**Digital voice** (D1/D2 = 7,7, reported as `2400V`) is the 2400S chain carrying a vocoder's
bit stream (SPEC_NOTES INT-019, measured on a real recording). The receiver ignores it unless
given `--voice`, and then writes the raw bits, never async-deframed. No vocoder is included:
§5.3.1.2 calls for STANAG 4198 (LPC-10e) or STANAG 4591 (MELPe), which an external program
must supply (see docs/PLAN.md, non-goals, for why).

## Simulating an HF channel

```sh
m110c-tx < message.txt | m110c-chan --preset "2 fading 2 ms 1 Hz" --snr 18 | m110c-rx
m110c-chan --paths 2 --delay-ms 5 --doppler 5 --snr 7 --seed 3 in.cf32 -o out.cf32
```

The Watterson model of Appendix E: two equal-power paths, a delay spread apart, each with
Rayleigh fading of the given Doppler spread, plus noise at an SNR measured in 3 kHz. Presets
cover every Table XVI condition. Output is reproducible from `--seed`. The receiver meets every
Table XVI condition in the simulated runs recorded in docs/PERFORMANCE.md.

## Development

```sh
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest               # all tests, including the slow ones (about 20 minutes)
pytest -m "not slow" # what CI runs
ruff check . && ruff format --check .
python tools/conformance.py          # regenerate docs/CONFORMANCE.md (about an hour)
pip install -e ".[notebook]" && python tools/build_notebook.py   # rebuild the notebook
python tools/toystack.py --quick     # link-layer experiments: traffic patterns, WAVs (below)
```

`tools/toystack.py` is a playground for what will ride on the modem (PLAN.md, S8): beacons,
chat, telemetry, a store-and-forward mail session, a fountain-coded file transfer, and a
transfer whose 110 mode is negotiated from measured SNR (this README is its default test
file; `--file` picks another). Each runs as real transmissions through the channel simulator
and the receiver, with air time, frames lost, end-to-end throughput, and WAV recordings as
sent and as heard. Its frame format and protocols are drafts for experiments, not decisions.

Tests on real recordings (`tests/acceptance/`) run when `M110C_RECORDINGS` names a
directory holding them at 9600 S/s; see docs/VALIDATION.md.
